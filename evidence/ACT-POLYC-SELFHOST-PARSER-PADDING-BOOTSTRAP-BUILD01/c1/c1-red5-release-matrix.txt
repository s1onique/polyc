STEP SEQUENCE IN THE WORKFLOW
  1 actions/checkout@v4          -> a CLEAN tree. NO ignored binaries survive.
  2 Install build dependencies
  3 Resolve version
  4 "Build native hcc":  make C_COMPILER=cc BUILD_TYPE=Release INSTALL_PREFIX=/usr/local
  5 "Build hcc for target" (cross leg only): a second cmake -S ./src -B ./build-x86_64
  6 "Build libtos": uses ./hcc-native to compile src/holyc-lib/all.HC into tos.s
  7 "Stage package": copies ./hcc
  8 "Smoke test" (non-cross legs): installs the package into a scratch prefix,
    compiles + runs a hello program through AOT and JIT
  9 "Create zip"
 10 "Attach to release" / "Upload artifact"

      Even once B1 is repaired, step 5 configures a SECOND cmake tree with
      -DCMAKE_OSX_ARCHITECTURES=x86_64. The production hcc there will link
      build/parser-padding-subject.o, which the native step 4 produced for
      arm64. Linking an arm64 Mach-O object into an x86_64 binary FAILS at
      link time. The cross leg therefore needs a TARGET-ARCHITECTURE padding
      object, and the workflow must build it with the cross compiler.
      Additionally, src/CMakeLists.txt:9 sets CMAKE_RUNTIME_OUTPUT_DIRECTORY
      to `../`, so the cross cmake tree at build-x86_64 writes its binary to
      the REPOSITORY ROOT, overwriting ./hcc. The workflow already works
      around this by copying ./hcc to ./hcc-native FIRST (release.yml:83),
      and step 7 stages ./hcc (the x86_64 one). That ordering is correct and
      must be preserved.
    DISPOSITION = COMPILER_BLOCKED_AT_ENTRY (B1) + CROSS_ARCH_DEFECT (B4).
