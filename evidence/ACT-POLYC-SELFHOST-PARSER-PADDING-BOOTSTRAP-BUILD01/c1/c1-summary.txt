DECISIVE MEASUREMENTS TAKEN AT C1
  M1  A clean clone at ffee58b, driven by that tree's OWN Makefile chain,
      reproduces the pinned producer identity EXACTLY:
        build/hcc-bootstrap04 sha256 =
          3b4474213efabcda30eb2d0c0610c6e23793f876896c8e21c5e18024b1ab40f6
        == the frozen LIBTOS_BOOTSTRAP_EXPECTED_SHA.      (M3_MATCH=YES)
  M2  That tree's stage0 sha256 =
        e1bb1cb5b8e9090d6c8822c196b882036e49133373c78ac2f6e4343c39ca125c
      == the Factory-recorded G0 baseline.
  M3  The compiler embeds its own git hash into the binary's bytes
      (src/CMakeLists.txt:29-36), so the producer's tree MUST be a real
      checkout AT the pinned commit. `git archive` is INFEASIBLE.
  M4  The pinned chain's own `test-prefix-install` dependency is a cycle
      that the C2 graph must break with an explicit producer.
  M5  The `@@N` asm-local-label defect is present in the PINNED tree's
      stage0 too (20 measured occurrences). Pre-existing, out of scope.
  M6  The current-tree stage0 DOES produce the parser-padding object,
      and the object is byte-reproducible:
        187a4de9465e8dbe3c640484b05540daaad4a3267dd1543a169e3c304b02d5b1
      == the value recorded in the closed predecessor HANDOFF
      (docs/factory/HANDOFF-ACT-POLYC-SELFHOST-PARSER-PADDING01.md:247).
      Measured over 3 consecutive compilations: identical every time.
  M7  The padding object CAN be produced for a foreign target architecture:
        ./hcc --target=x86_64-apple-darwin ... -> Mach-O 64-bit object x86_64
        ./hcc (native, aarch64)                -> Mach-O 64-bit object arm64
      This is what makes the release cross leg (B4) repairable.

C2 IMPLEMENTATION CONTRACT (derived from the frozen design)
  1. Build an ISOLATED legacy stage0 with delegation OFF, into
     build/host-stage0/, WITHOUT overwriting ./hcc.
  2. Construct a header-only bootstrap prefix containing ONLY
     include/tos.HH. No runtime archive. No global fallback.
  3. Compile the parser-padding object from the CURRENT tree's
     tools/bootstrap/selfhost-parser-padding.HC into
     build/parser-padding-subject.o, and verify the exported symbol
     _BootstrapCalcPadding and the object architecture.
  4. Configure/link the production hcc with delegation ON and a REAL
     object dependency (add_custom_command OUTPUT/DEPENDS), not an
     if(EXISTS) probe.
  5. Move the bootstrap04 configure-time FATAL_ERROR to install time
     WITHOUT weakening the SHA check.
  6. Materialize the pinned producer tree, drive it, verify its SHA
     against the FROZEN constant, and install it as
     build/hcc-bootstrap04.
  7. Make the release workflow produce a TARGET-ARCHITECTURE padding
     object for the cross leg.
