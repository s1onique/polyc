ROOT CAUSE OF THE PRE-EXISTING FAILURE (measured, for the record)
  The cap verifier is a PYTHON tool
  (scripts/quality/llvm-cap-table-verifier.py) that shells out to
  `hcc --print-cap-table`. Measured on the developer's warm tree:
    $ ./hcc --print-cap-table ; echo $?
    139            <- SIGSEGV
  i.e. the warm, non-LLVM build SEGFAULTS on that flag, so the verifier
  cannot load the capability table and reports
    "FAIL  could not load capability table from hcc --print-cap-table"
  which the harness surfaces as "could not read cap verifier output".

  Measured on the LLVM-enabled build produced by this ACT:
    $ ./hcc --print-cap-table ; echo $?
    0
    56 capability rows emitted
  So the Python verifier and the cap table are NOT the cause of the 4
  rows; the rows are the harness's SHAPE_DEPENDENT counter and the
  three sibling-opcode rows, which the pre-existing evidence already
  recorded identically.

  Note for the record: the cap verifier is a PYTHON tool, which is in
  tension with F-NO-PYTHON (docs/factory/DOCTRINE.md §26). It is
  PRE-EXISTING and separately owned; this ACT neither introduced nor
  touched it. It is recorded as residue.
