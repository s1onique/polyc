ACT-POLYC-LLVM-FLOAT01 / LLVM LangRef comparison-semantics binding
==================================================================

== Authority ==

The binding contract for the LLVM backend's F64 comparison
predicate selection is the LLVM Language Reference Manual
(llvm.org/docs/LangRef.html), independent of any PolyC native
backend. The native backends (aarch64, x86_64, JIT) are
witnesses to host behaviour, not authorities for LLVM IR
semantics.

== LangRef predicates and their IEEE-754 unordered semantics ==

For fcmp double operands where at least one is NaN:

  oeq : ordered and equal              NaN -> false
  ogt : ordered and greater than       NaN -> false
  oge : ordered and greater or equal   NaN -> false
  olt : ordered and less than          NaN -> false
  ole : ordered and less or equal      NaN -> false
  one : ordered and not equal          NaN -> false
  ord : ordered (no NaN operands)      NaN -> false
  ueq : unordered or equal             NaN -> true
  ugt : unordered or greater than      NaN -> true
  uge : unordered or greater or equal  NaN -> true
  ult : unordered or less than         NaN -> true
  ule : unordered or less or equal     NaN -> true
  une : unordered or not equal         NaN -> true
  uno : unordered (any NaN operand)    NaN -> true
  true : always true                   NaN -> true
  false: always false                  NaN -> false

The "ordered" predicates return false when either operand is NaN;
the "unordered" predicates return true. The "ord" and "uno"
predicates directly test for NaN involvement.

== PolyC's docs/CHARTER.md commitment ==

PolyC's language-level contract for F64 comparisons is the
standard C/IEEE-754 unordered convention: NaN compared to any
finite value yields false for == and the ordering relations,
and true for !=. This matches the LLVM ordered-predicate
semantics.

== ACT-POLYC-LLVM-FLOAT01 binding ==

The LLVM backend emits:

  ==  -> oeq    (PolyC commit: NaN -> false)
  !=  -> une    (PolyC commit: NaN -> true)
  <   -> olt    (PolyC commit: NaN -> false)
  <=  -> ole    (PolyC commit: NaN -> false)
  >   -> ogt    (PolyC commit: NaN -> false)
  >=  -> oge    (PolyC commit: NaN -> false)

These bindings are aligned with both the LLVM LangRef and the
PolyC charter. This is the only sensible cross-backend
contract: it preserves PolyC's source-level semantics regardless
of which LLVM target triple the backend emits for.

== Witness: aarch64 host (ARMv8.4-A reference) ==

Observed via aarch64 JIT probe (NZCV after `fcmp d0, d1` with
NaN operand):

  NZCV=0011  (binary 0011: N=0 Z=0 C=1 V=1)
  cset eq  -> 0    (matches oeq)
  cset ne  -> 1    (matches une)
  cset mi  -> 0    (matches olt)
  cset ls  -> 0    (matches ole)
  cset gt  -> 0    (matches ogt)
  cset ge  -> 0    (matches oge)

This witness is consistent with the LangRef ordered-predicate
semantics. It is recorded as a witness, not as an authority.

== Observed residue: x86_64 native backend (mechanically derived) ==

Source: src/x86_64.c lines 670-679 (x86_64CcFor, is_float==1
column) and lines 727-744 (x86_64EmitSetCC). The JIT path
(src/x86_64-jit.c lines 425-433) emits the same condition
codes via X86_CC_B/BE/A/AE/E/NE.

For IR_FCMP the PolyC x86_64 backend emits:

   IR_CMP_EQ -> sete      (ZF=1)
   IR_CMP_NE -> setne     (ZF=0)
   IR_CMP_LT -> setb      (CF=1)
   IR_CMP_LE -> setbe     (CF=1 || ZF=1)
   IR_CMP_GT -> seta      (CF=0 && ZF=0)
   IR_CMP_GE -> setae     (CF=0)

After `ucomisd` on NaN/unordered operands, x86 sets
ZF=1, PF=1, CF=1 (Felix Cloutier, UCOMISD pseudo-op
table; SETcc). Substituting:

   IR_CMP_EQ (sete,    ZF=1)              -> 1   WRONG; expected 0
   IR_CMP_NE (setne,   ZF=0)              -> 0   WRONG; expected 1
   IR_CMP_LT (setb,    CF=1)              -> 1   WRONG; expected 0
   IR_CMP_LE (setbe,   CF=1 || ZF=1)      -> 1   WRONG; expected 0
   IR_CMP_GT (seta,    CF=0 && ZF=0)      -> 0   CORRECT (matches ogt NaN->false)
   IR_CMP_GE (setae,   CF=0)              -> 0   CORRECT (matches oge NaN->false)

So FOUR of six PolyC FCMP predicates diverge from IEEE-754 /
LangRef on NaN inputs (EQ, NE, LT, LE). Two (GT, GE) already
produce the correct ordered-predicate result by accident of
the unordered flag state. Compiled truth table for the
PolyC x86_64 native backend (NaN operand):

  PolyC op   x86_64 native result on NaN   correct (LangRef/IEEE-754)   status
  --------   ---------------------------   -------------------------   ------
  ==         1                              0                            WRONG
  !=         0                              1                            WRONG
  <          1                              0                            WRONG
  <=         1                              0                            WRONG
  >          0                              0                            CORRECT
  >=         0                              0                            CORRECT

Defect set for the next ACT (must mask unordered on the four
broken predicates; must PRESERVE the two correct ones):

  EQ : sete  -> must mask unordered (currently returns 1; should return 0)
  NE : setne -> must include unordered (currently returns 0; should return 1)
  LT : setb  -> must mask unordered (currently returns 1; should return 0)
  LE : setbe -> must mask unordered (currently returns 1; should return 0)

Conservation controls (must NOT change):

  GT : seta  -> 0 on unordered (already matches ogt)
  GE : setae -> 0 on unordered (already matches oge)

This is a PolyC x86_64 NATIVE backend defect, not an LLVM
backend defect. It is OUT OF SCOPE for ACT-POLYC-LLVM-FLOAT01.

Note: the inline comment at src/x86_64.c:663-666
("we treat IR cmps as loose-ordered (matches aarch64's
behaviour)") is incorrect for the four broken predicates
(EQ, NE, LT, LE). The x86_64 unordered-flag dispatch
produces the OPPOSITE of the aarch64 host oracle on those
four predicates when at least one operand is NaN. For GT/GE
the dispatch happens to coincide with the aarch64 host
oracle (both return 0 on unordered). The two backends agree
on finite operands and on GT/GE NaN; they disagree on
EQ/NE/LT/LE NaN.

Recommended future ACT: ACT-POLYC-NATIVE-X86-FLOAT-CMP-PARITY01,
which would re-emit the x86_64 native FCMP lowering using
ordered-predicate equivalent sequences (e.g. `ucomisd + setnp /
setp + setz / setnz` or equivalent) so that == returns 0 on
NaN, the four orderings return 0 on NaN, and != returns 1 on
NaN -- matching both IEEE-754 and the LLVM LangRef.

== Verification: emitted .ll grep ==

Each emitted .ll file for the comparison fixtures contains
exactly one of `oeq`, `une`, `olt`, `ole`, `ogt`, `oge` and no
`ueq`, `ugt`, `uge`, `ult`, `ule`, `one`, `uno`. Verified in
evidence/llvm-float01/impl/comparison-predicate-map.txt.

== Conclusion ==

The LLVM backend's comparison semantics are bound to the
LLVM LangRef. The aarch64 host oracle (cset mi/ls/gt/ge/eq/ne
after fcmp on NaN) is consistent with that binding and
therefore corroborates it as a witness; it is not the
authority. The x86_64 native backend's FCMP lowering
diverges from IEEE-754 / LangRef on FOUR of six predicates
when at least one operand is NaN (EQ, NE, LT, LE), and
coincidentally matches the LangRef on the remaining two
(GT, GE, which return 0 on unordered by accident of the
UCOMISD CF=ZF=0 branch). That divergence is a separate,
non-blocking residue for
ACT-POLYC-NATIVE-X86-FLOAT-CMP-PARITY01; its defect set
binds to the four broken predicates listed above.
