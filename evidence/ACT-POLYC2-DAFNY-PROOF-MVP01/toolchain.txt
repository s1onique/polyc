Why this distribution was selected
----------------------------------
The Dafny 4.11.0 release ships three native artefacts on
GitHub:
  - dafny-4.11.0-arm64-macos-13.zip (standalone, with Z3)
  - dafny-4.11.0-x64-macos-13.zip  (x64 standalone)
  - dafny-4.11.0.nupkg              (.NET tool only)
The macOS arm64 standalone is the only artefact that:
  (a) is self-contained (includes Z3 binary, no PATH needed)
  (b) matches the host architecture (arm64)
  (c) is verifiable end-to-end via
      `dotnet DafnyDriver.dll --version` returning
      "4.11.0+fcb2042..." (not "0.0.0.0" which is what
      the nupkg-only path reports on this host).

dafny audit (text/HTML/Markdown/IETF report writer)
---------------------------------------------------
  dafny audit <files...> [--report-file PATH]
                           [--report-format txt|html|md|md-ietf]

dafny audit checks for, at minimum: assume statements,
{:axiom}, {:verify false}, {:extern} with contracts,
bodyless declarations with trusted postconditions,
bodyless forall used as assumption, bodyless loop used
as assumption.

Toolchain access from gate
--------------------------
scripts/quality/formal-dafny.sh puts
tools/dafny/dafny-4.11.0/dafny/z3/bin/ on PATH for
the duration of the gate run, but verification
itself does NOT rely on PATH-based auto-discovery:
the dafny verify call passes --solver-path "$Z3"
(I7), so the exact Z3 executable the gate
authenticated is the exact solver Dafny uses.
PATH is set only so that tools dafny invokes
transitively (e.g. for audit) still find a Z3
in the bundled tree if they look one up.

Runtime-pinned identities (CORRECTION01)
----------------------------------------
The stable gate scripts/quality/formal-dafny.sh
mechanically checks the following VERSION identities
BEFORE running any verification:

  EXPECTED_DAFNY_VERSION = 4.11.0+fcb2042d6d043a2634f0854338c08feeaaaf4ae2
  EXPECTED_Z3_PREFIX     = Z3 version 4.12.1

A mismatch causes the gate to exit 3 before any
verify/audit invocation.

This is a runtime VERSION pin. It is NOT a runtime
BINARY hash pin: the gate does NOT compare the SHA-256
of the `dafny` executable or the `z3` binary against a
recorded digest. Recorded digests (see Distinction of
digests below) are provenance information used during
provisioning and reproduced in evidence; they are
not re-checked on every gate run.

Scope of the runtime check:
  - dafny --version output must equal the expected
    string exactly;
  - z3 -version output must start with the expected
    prefix;
  - dafny verify is invoked with --solver-path
    pointing at the EXACT Z3 executable we just
    checked, so the solver Dafny uses is the same
    file we authenticated (not whatever PATH
    resolution would have picked).

Out-of-scope at runtime:
  - SHA-256 of the dafny executable
  - SHA-256 of the z3 executable
  - signing-key / notarisation validation
  - dependency-graph (e.g. .dll / .so) validation

If a content-identity invariant on the binary is
required, an additional hash check must be added to
scripts/quality/formal-dafny.sh and TOOLCHAIN_BINARY_
SHA_PIN_ENFORCED must be set to true.
