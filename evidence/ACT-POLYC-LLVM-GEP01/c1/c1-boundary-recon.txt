Q1 - What neutral IR does current PolyC frontend emit for
     `U8 *p; I64 i; p[i]` ?
  Source: src/tests/llvm-gep01/readat.HC
    I64 ReadAt(U8 *p, I64 i) { return p[i]; }
  Pre-optimisation neutral IR (paraphrased):
    i64 ReadAt(%p1 ptr param, %p3 i64 param) {
      bb1:
        store    %l2 ptr local, %p1 ptr param
        store    %l4 i64 local, %p3 i64 param
        alloca   %t5 i64 tmp, 8
        iadd     %t6 ptr tmp, %l2 ptr local, %l4 i64 local   <-- ADDR
        load*    %t7 i8 tmp, %t6 ptr tmp                     <-- LOAD
        zext     %t8 i64 tmp, %t7 i8 tmp
        store    %t5 i64 tmp, %t8 i64 tmp
        jmp bb2
      bb2:
        load     %t9 i64 tmp, %t5 i64 tmp
        ret      %t9 i64 tmp
    }
  Answer: IR_IADD  (followed by IR_LOAD_DEREF).
          NOT IR_GEP.  NOT IR_LEA.

Q4 - What are the operand roles and types ?
  IR_IADD(dst=PTR tmp, r1=PTR base, r2=I64 index)

  No scale is computed (sizeof(U8) = 1; src/ir.c:629-645).
  The address-mode fusion pass (irFuseIaddIntoMemAddressing
  in src/ir-optimise.c:768) MAY fold this IADD into the
  consuming LOAD_DEREF as disp=k or idx+scale=N. For U8
  the scale is 1; the fusion heuristic does not fold a
  1x scaled index (no SIB win on x86), so IR_IADD remains
  as a distinct instruction.

Q5 - Is one existing opcode already intended to mean typed
     element-address computation ?
  NO.  IR_IADD with ptr+ptr+i64 -> ptr is integer addition
  that happens to be applied to pointer operands. The
  neutral-IR contract does NOT designate it as
  "typed element-address computation". The IR_GEP opcode
  IS the neutral-IR opcode whose semantic name is
  "get element pointer (array/struct indexing)"
  (src/ir-types.h:86), but the canonical lowerer
  (src/ir.c) does NOT emit it for pointer arithmetic.

  IR_LEA is reserved for "dst = &r1 (address of a stack
  slot, as a pointer)" (src/ir-types.h:85). It is the
  address-of a stack-allocated local, not an indexed
  address.

  Answer: NO.  No existing neutral-IR opcode is designated
  as "typed element-address computation" for byte indexing.

Q6 - Would choosing the other opcode duplicate or contradict
     its existing semantic intent ?
  N/A.  Neither IR_GEP nor IR_LEA is currently emitted by
  the canonical lowerer for `p[i]` of bytes.

Q7 - Is the existing IR_IADD shape sufficient for a GEP
     lowering without neutral-IR widening ?
  YES.  The IR_IADD shape `dst=PTR, r1=PTR, r2=I64` carries:
    - base pointer (r1, IR_TYPE_PTR)
    - scalar I64 index (r2, IR_TYPE_I64)
    - pointer result (dst, IR_TYPE_PTR)
    - exactly one index operand (r2 only)
  which matches the ACT §3 frozen target shape (BASE +
  one I64 INDEX -> PTR). The LLVM backend can recognise
  this exact IR_IADD subset at the dispatch seam and emit
  LLVMBuildGEP2(i8, base, [idx]) instead of LLVMBuildAdd.

  No neutral-IR widening is required: the existing
  IR_IADD opcode and its operand layout are exactly
  what the B0 byte-indexing shape needs.

  Answer: YES.  Per ACT §4 hard rule "Implement one
  existing neutral opcode", IR_IADD is the single
  consumed opcode.

Negative boundary preservation
------------------------------------------------------------
  Non-I8 element indexing is rejected at IR_LOAD_DEREF by
  the existing MEMORY01 disp/idx/scale guards. The I64
  element case is pre-folded into LOAD_DEREF::scale=8 by
  the address-mode fusion pass; the IMPL never sees an
  IR_IADD with ptr+ptr+i64 shape for I64-element indexing.

  For byte indexing specifically, the IR_IADD subset is
  byte-type-consistent by construction: the scale is
  always 1 (no IR_IMUL emitted), so no folded
  scale!=1 reach the LOAD_DEREF arm, and the consumer is
  a byte-shaped IR_LOAD_DEREF.
