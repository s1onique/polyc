## Semantic change in src/parser.c::CalcPadding

```c
int CalcPadding(int offset, int size) {
#ifdef HCC_USE_SELFHOST_PARSER_PADDING
    extern long long BootstrapCalcPadding(long long offset, long long size);
    return (int)BootstrapCalcPadding((long long)offset, (long long)size);
#else
    /* Stage0 evidence path: legacy C algorithm */
    if (size == 0) return 0;
    return offset % size == 0 ? 0 : size - offset % size;
#endif
}
```

The legacy algorithm body is preserved inside the `#else` branch for
the differential's stage0 oracle. The production path (with
`HCC_USE_SELFHOST_PARSER_PADDING` defined) routes exclusively through
`BootstrapCalcPadding`.

## Build wiring in src/CMakeLists.txt

A new option `HCC_USE_SELFHOST_PARSER_PADDING` (default ON) is added
immediately after `add_executable(hcc ...)`. When ON, CMake:

* defines `HCC_USE_SELFHOST_PARSER_PADDING` for the production hcc
  target;
* links `build/parser-padding-subject.o` into hcc.

The subject object is searched at `${CMAKE_SOURCE_DIR}/../build/parser-padding-subject.o`
(the existing convention; also the default location produced by
`make parser-padding-component`). If the file is missing, CMake
errors out with a clear build instruction.

## Why a dedicated macro

The generic `HCC_USE_SELFHOST_COMPONENTS` flag activates ALL lexer
delegations in src/lexer.c (BootstrapScanIdent, BootstrapClassifyOperator,
BootstrapScanScalarLiteral, BootstrapScanTrivia, BootstrapLinkDirective).
Enabling it for production hcc would require linking all five lexer
subject objects — out of scope for this ACT.

The dedicated `HCC_USE_SELFHOST_PARSER_PADDING` flag isolates the
parser-padding migration so it can land independently. The C3
verification confirms this isolation is correct: production parser
output is byte-identical to the legacy-C baseline.
