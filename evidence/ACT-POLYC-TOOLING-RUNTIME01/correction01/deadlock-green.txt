GREEN evidence: corrected SpawnAndCapture drains both pipes

Subject: src/holyc-lib/tooling.HC (corrected in CORRECTION01)
Fix:     replaced sequential drain with single poll(2) loop over
         both read-ends. On any revents (POLLIN | POLLHUP | POLLERR)
         attempt read; only close when read returns 0 (true EOF).
         This eliminates the block-then-read dependency.

------------------------------------------------------------
Architecture (corrected)
------------------------------------------------------------

  while (out_open || err_open) {
    poll(pfds[2], -1);          // wait for either side
    if (out_open && pfds[0].revents & ANY) {
      n = read(out_fd[0], ...);
      if (n > 0) drain; else close;
    }
    if (err_open && pfds[1].revents & ANY) {
      n = read(err_fd[0], ...);
      if (n > 0) drain; else close;
    }
  }

  // Why this is correct:
  // * poll(2) atomically waits on both fds — no block-then-read.
  // * Closing on read==0 (EOF) means the kernel has confirmed
  //   the writer is gone AND the buffer is drained.
  // * POLLHUP no longer triggers an immediate close — we always
  //   try to read first, which is the only way to capture any
  //   bytes the kernel still has buffered after the writer
  //   closed.

Why POLLHUP-before-EOF matters (sub-bug found in CORRECTION01)
------------------------------------------------------------

  The first correction01 attempt (sequential event check
  followed by immediate close on POLLHUP) DID break the deadlock
  but lost the last ~57 KiB of stderr bytes in the 4 MiB flood.
  Root cause: when child exits, kernel signals POLLHUP on
  stderr's read-end while the pipe buffer still contains
  un-flushed bytes. Closing immediately discards them.

  Final fix: the inner branch is now
    if (revents & (POLLIN | POLLHUP | POLLERR)) {
      n = read(...);
      if (n > 0) drain else close;
    }
  This way POLLHUP triggers ONE more read attempt, which returns
  whatever is left in the kernel buffer (often the last write
  before exit + the sentinel), then returns 0 on the next poll,
  at which point we close.

  Without this sub-fix, the corrected runtime would have lost
  7 chunks + sentinel (57 360 bytes) in the stderr-flood mode,
  producing "sentinel missing" instead of "sentinel found".
