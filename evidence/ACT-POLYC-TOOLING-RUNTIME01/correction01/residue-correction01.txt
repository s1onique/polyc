  rc=127 ambiguity in SpawnAndCapture (NEW, honestly documented)
    The current SpawnAndCapture treats both "execv failed
    in the child" and "child exited with code 127" as
    indistinguishable from the parent's perspective. Both
    collapse to rc=127 via WaitDecode. This was already true
    in the original C2 IMPL; CORRECTION01 did not change
    it. Per F13 (evidence over prose), we acknowledge the
    ambiguity here rather than claim non-existent precision.

    Possible design (NOT implemented in CORRECTION01):
      - Have child write a 1-byte status (0 = execv_ok,
        1 = execv_failed, then errno) to a small third pipe
        BEFORE the execv call.
      - Parent reads status pipe first; if execv_failed,
        return rc=-1 with errno propagated via an out-param.
      - If execv_ok, proceed with current logic.
    This would make the SpawnAndCapture API:
        I64 rc = SpawnAndCapture(...);  // current
        // vs
        I64 rc = SpawnAndCaptureEx(..., I32 *execv_errno);
    Cost: ~30 LOC + a third pipe + careful wait ordering.
    Benefit: unambiguous "couldn't start" vs "started and
             exited 127".
    Owner: Track B / tooling-runtime.
    Action: future ACT only if a caller actually needs
            this distinction (e.g. a lint runner that
            distinguishes "tool not installed" from
            "tool found a 127-error in its data").

  Project-wide trailing-blank-EOF hygiene (NEW)
