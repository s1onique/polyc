R0 CONSISTENCY CORRECTION
--------------------------
The RECON04 ranking table VIOLATED its own stated invariant that "R0
is MECHANICALLY the same value the eligibility checker used as its
clause 03 input": CAND-022 and CAND-023 had facts_r0=1 but
dims_r0=0.  RECON05 CORRECTS both to R0=1, so the ranking and the
eligibility fact cannot drift apart.  The correction is recorded in
c2/ranking-dimensions.tsv.

THE SELECTION, AND WHY IT IS NOT SUB-002
-----------------------------------------
The canonical ranker selected SUB-002.  The EXECUTABLE CAUSALITY GATE
then FAILED for SUB-002, so it was removed from the feasible subset by
a machine-verifiable reason and the selection was RE-RUN.

SUB-002's live condition tests FIVE AstKind values (AST_COMPOUND_STMT,
AST_CASE, AST_BREAK, AST_RETURN, AST_GOTO).  The already-migrated
SUB-001 decision tests the SAME FIVE plus AST_DEFAULT.  AST_DEFAULT is
UNREACHABLE at that position: a nested default raises "Duplicate
default case" and the inner parseDefaultStatement never returns.

THIS WAS PROVED BY EXECUTION, NOT BY ARGUMENT.  A mutant that ADDS
AST_DEFAULT to the SUB-002 condition was built into the REAL compiler
in a disposable worktree and the full 90-file production suite was run
with it:

  PRISTINE  376/376  md5=b6f117eb1386ca80f81bc06226e2a741
  MUTANT    376/376  md5=b6f117eb1386ca80f81bc06226e2a741

The assertion sequences are BYTE-IDENTICAL.  The mutation has ZERO
observable effect, so SUB-002 is DUPLICATED CODE, not a distinct
decision.  Transferring it would create a SECOND PolyC authority for a
decision the first authority already owns.

  IC-01  a per-row checker cannot see a DELETED row, so the RECON05
