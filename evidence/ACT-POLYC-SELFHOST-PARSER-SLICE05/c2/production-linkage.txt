THE VERIFIER TARGET
--------------------
  add_custom_target(hcc-ast-unary-token-map-verify
    COMMAND cmake -DAST_TOKEN_MAP_OBJECT=...
            -DAST_TOKEN_MAP_EXPECTED_SYMBOL=BootstrapAstUnaryOpFromToken
            -DAST_TOKEN_MAP_TARGET_OBJECT_FORMAT=...
            -DAST_TOKEN_MAP_NM=...
            -P src/cmake/VerifyAstTokenMapObject.cmake
    COMMAND cmake -DAST_TOKEN_MAP_OBJECT=...
            -DAST_TOKEN_MAP_STAMP=...
            -P src/cmake/WriteAstTokenMapObjectStamp.cmake
    DEPENDS ${AST_UNARY_TOKEN_MAP_OBJECT})

  The verification is a custom TARGET, so its command ALWAYS runs.
  A custom command with an OUTPUT file would be considered
  up-to-date whenever that file exists -- the stale-stamp hazard.
  The stamp file is a RECORD of a successful verification, never
  the thing that decides whether a verification happens.

  The verification GATES THE LINK:
    add_dependencies(hcc hcc-ast-unary-token-map-verify)
    set_property(TARGET hcc APPEND PROPERTY LINK_DEPENDS ...)

  The production compiler is therefore never linked without a
  verified PolyC AST-unary authority.

  The unary subject passes the SAME generic verifier that the
  binary subject passes, with the unary expected symbol.  There is
  no second, weaker verifier to drift.

    target_compile_definitions(hcc PRIVATE HCC_USE_SELFHOST_PARSER_AST_UNARY)

  The production compiler is compiled WITH the delegation macro and
  links the unary subject.  The stage0 compiler is compiled WITHOUT
  it (-DHCC_USE_SELFHOST_PARSER_AST_UNARY=OFF), which is what breaks
  the bootstrap cycle: the stage0 compiler produces the subject, so
  it cannot require it.
