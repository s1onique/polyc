# collapse-recon.md -- RESUME01 C1 RED causal recon

Mechanical identification of the SSA-dominance defect in the IR
builder's exit-block lowering. This recon is purely observational;
no production code is changed in this commit (RED phase only).

---

## 1. The verifiable RED

```
$ ./hcc --install-dir=/tmp/polyc-install --emit-llvm \
    src/tests/llvm-byte-memory01/pos_b0_compare_digit.HC

LLVM backend capability contract: ok (56 rows, ordinal binding)
LLVM_BACKEND_VERIFY_FAILED: Instruction does not dominate all uses!
  %i8_arith_zext = zext i8 %3 to i64
  ret i64 %i8_arith_zext

  %6 = add i64 %5, %i8_arith_zext
  ret i64 %6

```

The hcc binary compiles the source through `irLowerFunction` →
`irBasicFunctionOptimisations` → LLVM 22 C-API emission, then runs
`LLVMVerifyModule(mod, LLVMReturnStatusAction, ...)` and aborts
when the module is not verifier-valid. The module-level verifier
is therefore the actual user-visible gate; the per-function
verifier is not called separately. (Per the IMPL at line 2317.)

## 2. The two-level pipeline

The transformation pipeline for an I64 / I8 / byte function is:

```
source.HC
  → parser
  → AST
  → irLowerFunction (src/ir-lower.c)
      → raw IR with alloca + store + load + ret
  → irBasicFunctionOptimisations (src/ir-optimise.c)
      → irRemoveAllNops
      → irRemoveRedundantBlocks
      → irFoldPassThroughBlocks      ← folds bb6 (jmp bb4) into bb3 (br bb5,bb4)
      → irRemoveRedundantBlocks
      → irFoldGlobalDeref
      → irForwardReturnSlot          ← THIS is the rewrite under suspicion
      → const-fold + store-forward fixed-point
      → irDeadStoreEliminate
      → iadd-fuse + load-op-store fixed-point
      → irRemoveAllNops
  → llFunction (src/llvm-backend.c)
      → llDetectCollapsibleReturn    ← LLVM-side collapse seam
      → llLowerBlock per block
      → LLVMBuildRet / LLVMBuildBr
  → LLVMVerifyModule                ← THIS rejects the result
```

`llCollapseStoreValue` (line 491) and `llDetectCollapsibleReturn`
(line 400) form the LLVM-side collapse seam. They require, for
each predecessor `pb` of the exit_block, exactly one
`store slot, V` immediately before `jmp exit_block`.

The two-stage shape — `store slot, V` in each predecessor +
`load slot; ret load_result` in exit_block — is exactly the
PolyC return-slot idiom generated by `irLowerFunction` for
`return X` expressions.

## 3. Definition / use / dominance matrix for pos_b0_compare_digit.HC

After `irBasicFunctionOptimisations`, the neutral IR for
`ReadDigit` is (full dump in pos-b0-before.ir):

```
bb1 -> successors: {3, 4}                 ← entry
  store    %l8 = 0
  load*    %t5 = *p                       ← byte load (IR_LOAD_DEREF, byte access)
  zext     %t6 = %t5
  trunc    %l4 = %t6                      ← byte local c
  zext     %t9 = %l4
  cmp_ge   %t10 = %t9, 48
  br       %t10 -> bb3, bb4

bb3 -> predecessors: {1}  successors: {5, 4}
  zext     %t11 = %l4
  cmp_le   %t12 = %t11, 57
  br       %t12 -> bb5, bb4

bb5 -> predecessors: {3}  successors: {4}
  zext     %t13 = %l4
  isub     %l8 = %l8, %t13, 48           ← conditional modification of return local
  jmp      bb4

bb4 -> predecessors: {1, 3, 5}  successors: {4}
  ret      %l8                           ← single instruction (rewritten by
                                           irForwardReturnSlot)
```

Mechanical identification:

| role         | block | instruction                   |
|--------------|-------|-------------------------------|
| definition   | bb5   | isub %l8 = %l8, %t13, 48      |
| (consumer / use) | bb4 | ret %l8                      |
| predecessors of bb4 | bb1, bb3, bb5 |                       |
| predecessors that define %l8 | bb5 only |                   |
| predecessors that DON'T define %l8 | bb1, bb3 |            |
| definition dominates bb4? | bb5 → bb4: YES |                 |
| bb1's path to bb4 defines %l8? | NO (bb1 only reads %l8)   |
| bb3's path to bb4 defines %l8? | NO (bb3 only reads %l4)    |

Conclusion: **bb4 uses %l8, but %l8 is defined only on the
bb5 → bb4 path. The bb1 → bb4 and bb3 → bb4 paths reach bb4
without a definition of %l8.**

When the LLVM backend lowers this to textual LLVM IR, the
`zext %t9 = %l4` in bb1 and `zext %t11 = %l4` in bb3 are emitted
in those blocks (they are not collapsed), but the value
`%i8_arith_zext` (= %l4 after byte → I64 zext) used by the
ultimate `ret %l8` (= `ret (iadd 0, %l8)` after further rewrites)
in bb4 has no single defining instruction that dominates bb4.

The `where llCollapseStoreValue made the unsafe choice` answer:

`llCollapseStoreValue` does NOT participate in this defect.
`llDetectCollapsibleReturn` rejects the post-opt IR at the
`exit_block has n=1 instruction (only `ret %l8`), not 2
instructions` guard at line 416, so the LLVM-side collapse is
NOT applied. The defect is upstream, in the **neutral IR
optimisation pass** that rewrote
`store slot, %l8; load slot; ret load_result`
in the pre-opt exit_block into
`ret %l8`
in the post-opt exit_block.

The rewrite is `irForwardReturnSlot` at src/ir-optimise.c line 256.
It is intra-block: it walks each block, finds the
`store; load; ret` triple inside that block, and rewrites it
to `ret stored_value`. The optimisation does NOT verify that
every predecessor of the exit_block defines `stored_value`.
The PolyC IR has register-promoted locals (`%l8`, `%l17` etc.)
that are assigned by SSA definitions in one branch and read in
the exit_block; when the rewrite happens, the exit_block's
`ret %l8` references a value that may not dominate the
exit_block along every predecessor path.

## 4. CFG-shape classification

I built five probe fixtures to map the trigger:

| fixture                                 | shape                                | result |
|-----------------------------------------|--------------------------------------|--------|
| `trivial_probe.HC` (`if x>=10 return 1; return 0;`) | return literals in both arms | PASS |
| `uncond_probe.HC` (`acc = acc + x; return acc;`)    | unconditional modification | PASS |
| `readonly_probe.HC` (`return x; return 0;`)        | local read, not modified | PASS |
| `single_cond_probe.HC` (`if x>=10 acc+=x; return acc;`) | local modified inside one `if` | **FAIL** (verifier rejects) |
| `i64_collapse_probe.HC` (same shape, I64-only)      | local modified inside nested diamond | **FAIL** |
| `pos_b0_compare_digit.HC` (I8 + nested diamond)    | byte local modified inside nested diamond | **FAIL** |

Triggering condition: **a function-local whose value is the
function's return value, where the local is conditionally
modified inside a conditional branch.**

The defect is NOT byte-specific. It reproduces with I64-only
fixtures that share the same CFG shape (single conditional or
nested diamond with local modification). The byte fixture
(`pos_b0_compare_digit.HC`) is the first BYTE-MEMORY01 fixture
that exposes the generic defect because byte handling happens
to use the same local-modification + conditional-return pattern.

---

## 5. Where the unsafe choice lives -- precise answer

The unsafe choice is the **intra-block `store; load; ret`
rewriting in `irForwardReturnSlot` (src/ir-optimise.c:256-309)
applied to the exit_block**.

Specifically, the line 287 rewrite
```c
rt->dst = st->r1;
```
replaces `ret %tmp_loaded` with `ret %stored_value` where
`%stored_value` is the value stored to the return slot. The
optimisation assumes that `%stored_value` is available at the
exit_block (it is — the `store` is in the same block as the
`ret`), but it does not verify that `%stored_value` is a
dominating value with respect to the exit_block's predecessor
set. When the return local has multiple definitions across
predecessors and only some predecessors define it, the rewrite
produces SSA-invalid IR.

## 6. Root cause class

```
ROOT_CAUSE_CLASS = generic LLVM builder CFG bug
TRIGGERED_BY      = BYTE-MEMORY01 B0 fixture pos_b0_compare_digit.HC
SEAM              = src/ir-optimise.c irForwardReturnSlot line 287
                  rt->dst = st->r1;
EFFECT            = exit_block's ret uses a value that does not
                  dominate the exit_block along every predecessor
                  path
```

This is NOT a byte-only defect. The I64-only probe
`i64_collapse_probe.HC` reproduces the same verifier failure
with no IR_TYPE_I8 involvement. RESUME01's authorised
llCollapseStoreValue seam (`src/llvm-backend.c`) is one
containment site; the upstream `irForwardReturnSlot` seam
(`src/ir-optimise.c`) is the other containment site and is the
actual root cause.

The IMPL closure record from BYTE-MEMORY01 §0.5 H2 named
"llCollapseStoreValue cross-block reload missing" as the
defect; that hypothesis is now DEMOTED to "one of two
containment sites." The actual root cause is the IR
optimisation pass. RESUME01 must address BOTH sites (or, if
one site alone is sufficient to suppress the defect, that
one site with a documented rationale).
