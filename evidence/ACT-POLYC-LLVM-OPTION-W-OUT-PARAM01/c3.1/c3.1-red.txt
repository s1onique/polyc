OUTCOME: B (per the expert's trichotomy):

  - Outcome A (LLVM value already i8): NO -- the IR_ICMP incoming
    edge is i1, not i8.
  - Outcome B (LLVM value i1): YES -- the IR_ICMP incoming edge
    lowers to LLVM i1. C4 must insert an explicit i1 -> i8
    conversion before LLVMAddIncoming for that edge.
  - Outcome C (LLVM value i64): NO -- no i64 incoming edges exist
    in the current fixture set (G3/PhiOnly).
  - Outcome D (neutral IR inconsistent): NO -- the neutral IR is

C4 IMPL-B REQUIRED-AUTHORIZATION UPDATE:

  The C3-decided authorization (LLVMBuildPHI + LLVMAddIncoming +
  existing llLowerValue + existing llLowerType + existing
  llGetOrCreateBlock) is INSUFFICIENT.

  Required addition: a single, narrowly-scoped boolean
  normalisation for IR_ICMP-produced incoming edges:

    For each incoming edge (value, block) of an IR_PHI:
      if (cached_value type == LLVMInt1TypeInContext(lc->ctx) &&
          phi type == LLVMInt8TypeInContext(lc->ctx)):
        LLVMValueRef norm = LLVMBuildZExt(
            lc->bld, cached_value,
            LLVMInt8TypeInContext(lc->ctx),
            "phi_icmp_zext");
        use norm as the incoming value to LLVMAddIncoming.
      else:
        use cached_value as-is.

  This conversion is correct because:
    (a) IR_ICMP always returns {0, 1} per its semantic contract
        (the IR_BR dispatch at src/llvm-backend.c:1815-1872 has
        been the runtime witness for i1 == {0, 1} since
        ACT-POLYC-LLVM-CORE01-CORRECTION01).
    (b) zext of {0, 1} -> i8 is the identity bit-pattern.
    (c) The result participates in the i8 PHI exactly as the
        neutral IR intended: a 0/1 boolean widened to byte width.

  NO scope expansion:
    - No new diagnostic macros.
    - No new counter increments.
    - No change to Gate 3 / Gate 4 / Gate 5 logic.
    - No change to llType or llLowerValue.
    - The conversion lives entirely inside the proposed IR_PHI
      dispatch arm's incoming-edge iteration loop.

  The conversion IS technically a general i1 -> i8 widening,
  but it is bound to the IR_PHI dispatch arm's incoming-edge
  handling, not a general integer-conversion widening. Per the
  expert's guidance, the contract is named "short-circuit PHI
  incoming normalization only" (the i8 PHI is exclusively the
  short-circuit-compare result; a non-i8 PHI would need
  different / additional contracts which are out of scope).
