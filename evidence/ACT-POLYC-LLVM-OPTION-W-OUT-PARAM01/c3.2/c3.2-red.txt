ACT-POLYC-LLVM-OPTION-W-OUT-PARAM01 C3.2 RED: PHI incoming-edge normalisation placement
=====================================================================================

QUESTION (per expert review):
  The C3.1 amendment placed the i1 -> i8 zext INSIDE the merge
  block (after the PHI). The expert identified that this is a
  DOMINANCE violation: LLVM requires a PHI incoming value to be
  defined on the predecessor edge, not inside the merge block.
  Q: is the dominance violation mechanically reproducible, and
     is the corrected geometry (zext in predecessor before
     its terminator) mechanically accepted by the LLVM verifier?

CORRECTED §9.1 ALGORITHM (C3.2)

  for each incoming edge (value, predecessor) of an IR_PHI:
    v := llLowerValue(lc, value)
    if LLVMTypeOf(v) == LLVMInt1TypeInContext(lc->ctx) &&
       phi_ty == LLVMInt8TypeInContext(lc->ctx):
      /* Materialise the conversion on the predecessor edge:
         position builder BEFORE the predecessor terminator,
         emit zext, restore builder to merge block. */
      pred_bb := llGetOrCreateBlock(lc, p->ir_block)
      pred_term := LLVMGetBasicBlockTerminator(pred_bb)
      save_block := LLVMGetInsertBlock(lc->bld)
      LLVMPositionBuilderBefore(lc->bld, pred_term)
      v := LLVMBuildZExt(lc->bld, v,
            LLVMInt8TypeInContext(lc->ctx),
            "phi_icmp_zext")
      LLVMPositionBuilderAtEnd(lc->bld, save_block)
      LL_INC_SHAPE_DEPENDENT(lc)
    use v as the incoming value to LLVMAddIncoming

PREDECESSOR-MATERIALISATION INVARIANTS

  C3.2 also freezes three preconditions the C4 implementation
  must satisfy:

  PI-1  the incoming predecessor LLVM block already exists
  PI-2  the incoming predecessor LLVM block has a terminator
  PI-3  the incoming icmp/lower value has already been
        materialised in the predecessor block

  These hold by the preorder proof already recorded in the ACT
  (current short-circuit producer: incoming predecessor block
  < merge block in backend traversal order). The C4
  implementation must runtime-assert these before calling
  LLVMGetBasicBlockTerminator.

  If any of PI-1, PI-2, PI-3 fails at PHI-lowering time:
  HALT_PHI_EDGE_MATERIALIZATION_REQUIRED

DOMINANCE WITNESS RECAP

  The exact verifier diagnostic observed:

    Instruction does not dominate all uses!
      %z = zext i1 %cmp to i8
      %phi = phi i8 [ %z, %pred ]

  This matches the LangRef rule: "The use of a PHI node's
  incoming values occurs in the predecessor basic block."
  (see LLVM Language Reference Manual, §PHINode semantics).

  The geometric fix is the standard LLVM transformation
  pattern for inserting instructions on a PHI operand edge:
  reposition the builder to the predecessor, emit, reposition
  back. (LLVMPositionBuilder* family is in llvm-c/Core.h.)
