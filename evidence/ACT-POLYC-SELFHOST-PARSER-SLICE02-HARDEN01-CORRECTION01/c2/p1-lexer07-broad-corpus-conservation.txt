# ---- WHY THE TWO COUNTS DIFFER (15 vs 21) -------------------------
#
# The registry's BASELINE_FAILURE_COUNT of 21 is the sum of its three
# disjoint classes:
#
#   NO_FALLBACK_S0_COUNT   9   (stage0 fails, no historical fallback)
#   ALL_FAIL_4_COUNT       6   (all four stages fail)
#   S0_DIVERGED_..._COUNT  6   (stage0 diverges from s1..s3)
#                             ----
#                             21
#
# The OBSERVED run has 9 NO_FALLBACK and 6 ALL_FAIL, and 0
# S0_DIVERGED. The 6 S0_DIVERGED sources (fzf, json, net, set,
# sqllite, stat) are NOT observed as failures in this run: they
# compile at stage0 and are byte-identical across the four stages, so
# they are counted in PASS_S0/PASS_S1..S3 rather than in the failure
# set. The registry classified them as S0_DIVERGED at the time it was
# established; today they do not diverge.
#
# The OBSERVED failure set is therefore a STRICT SUBSET of the
# BASELINE failure set: every source that fails today also failed in
# the baseline, and no source that passes today failed in the
# baseline. That is CONSERVATION in the direction the registry's
# forward contract requires:
#
#   FORWARD_NEW_FAILURE_IDENTITIES_TOLERANCE   0
#   FORWARD_REMOVED_PASS_IDENTITIES_TOLERANCE   0
#   FORWARD_NEW_DIVERGENCES_TOLERANCE           0
#   FORWARD_NEW_PASS_MISMATCHES_TOLERANCE       0
#
# The 9 PASS_MISMATCHes the tool reports are exactly the 9
# NO_FALLBACK sources: stage0 fails for them and there is no
# historical fallback (build/b02-corpus-A is not present in this
# tree), so the tool records a pass mismatch. The registry's baseline
# classifies the SAME 9 sources as NO_FALLBACK_S0_COUNT=9 with the
