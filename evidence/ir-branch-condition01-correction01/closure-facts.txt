Closure-loop identity binding (extended contract for
closure-requalification ACTs):

The standard closure-loop contract for a CORRECTIONnn ACT is:
    SUBJECT = HEAD~   (substantive commit is HEAD~)

For a closure-requalification ACT (this one), the SUBJECT is
the implementation commit that was actually tested by gate-push.
The implementation commit is not at HEAD~ — it is at HEAD~N for
some N >= 2 because the closure-requalification ACT itself adds
the corrected-closure contract as intermediate commits.

This CORRECTION01 therefore uses the extended contract:

    SUBJECT is the impl commit (cbf726ed9399).
    Depth from any descendant HEAD to SUBJECT is computed:
        DEPTH := git rev-list --count $SUBJECT..HEAD
    The impl commit is reached from HEAD by:
        HEAD~DEPTH == SUBJECT
    DEPTH is never prescribed; only computed.

Why N=3 (not N=1 or N=2)?

  In the standard closure-requalification ACT pattern
  (substantive + closure), HEAD~ IS the substantive commit.
  Here, the substantive commit is a documentation/commit-
  organization commit, not the implementation commit. The
  gate-push was run against the IMPLEMENTATION commit
  (cbf726e), not against the documentation commit (574840d).
  Documenting the gate-push as if it were run against 574840d
  would be a false-GREEN.

  N=2 was the historical depth from the closure-evidence commit
  (de90851). After the loop-breaker commit (50a158e) was added,
  the CORRECTION01-final depth became N=3. CORRECTION03 replaces
  the fixed N with the dynamic DEPTH rule above.

  The gate-push output is invariant under subsequent commits on
  top of the impl commit (subsequent ACTs only modify docs/ and
  evidence/, never src/), so SUBJECT=cbf726ed9399 remains the
  authoritative impl commit, and DEPTH always reaches it from
  any descendant HEAD.

Mechanical verification recipe (canonical, amend-resilient):

    cd /Volumes/UserData/Users/chistyakov/Projects/SPbNIX/polyc
    SUBJECT=$(grep '^SUBJECT=' \
        evidence/ir-branch-condition01-correction01/gate-push-impl/log.txt \
        | head -1 | cut -d= -f2)
    SUBJECT_FULL=$(git rev-parse "$SUBJECT^{commit}")
    DEPTH=$(git rev-list --count "$SUBJECT_FULL"..HEAD)
    BOUND=$(git rev-parse "HEAD~$DEPTH")
    ANC=$(git merge-base --is-ancestor "$SUBJECT_FULL" HEAD \
         && echo yes || echo no)
    test "$SUBJECT_FULL" = "$BOUND" && test "$ANC" = "yes" \
        && echo PASS || echo FAIL

  This recipe (a) resolves the short gate SHA to a full 40-char
  SHA via $SUBJECT^{commit}, (b) computes DEPTH dynamically,
  (c) asserts HEAD~DEPTH equals the full impl SHA, and (d)
  asserts SUBJECT is an ancestor of HEAD (which it must be,
  since the impl commit is on main and HEAD is a descendant).

  No snapshot, no fixed N. Re-running this recipe at any
  descendant HEAD will produce PASS as long as SUBJECT is
  unchanged.
