Closure-loop identity binding (extended contract for
closure-requalification ACTs):

The CORRECTION03 closure-loop contract is:
    SUBJECT = HEAD~   (substantive commit is HEAD~)

For a closure-requalification ACT (this one), the SUBJECT is
the implementation commit that was actually tested by gate-push.
The implementation commit is not at HEAD~ — it is at HEAD~N for
some N >= 2 because the closure-requalification ACT itself adds
the corrected-closure contract as intermediate commits.

This CORRECTION01 therefore uses the extended contract:

    SUBJECT = HEAD~N where N is the depth to the impl commit

Why N=3 (not N=1 or N=2)?

  In the standard CORRECTION03 pattern (substantive + closure),
  HEAD~ IS the substantive commit. Here, the substantive commit
  is a documentation/commit-organization commit, not the
  implementation commit. The gate-push was run against the
  IMPLEMENTATION commit (cbf726e), not against the documentation
  commit (574840d). Documenting the gate-push as if it were run
  against 574840d would be a false-GREEN.

  N=2 was the depth from the closure-evidence commit
  (de90851). After the loop-breaker commit (50a158e) was added,
  the depth became N=3 (HEAD~3 from FINAL_HEAD = impl).

  The gate-push output is invariant under the loop-breaker
  addition (it only modifies the HANDOFF identity section, not
  the captured log), so SUBJECT=cbf726ed9399 remains correct
  and the only required change is the N bookkeeping.
