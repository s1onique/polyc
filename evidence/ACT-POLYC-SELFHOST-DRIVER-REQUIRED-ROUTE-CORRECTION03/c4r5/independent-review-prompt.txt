The probe exercises the PRODUCTION functions. It does not carry a

THE PROBE'S INTEGRITY IS THE FIRST THING TO CHECK.

The probe is the instrument that decides whether the repairs hold. If the
probe is wrong, the repairs are unproven. Look for:

  * a control whose EXPECTATION is inverted, so that it passes when the
    production function is wrong;

  * a control that does not exercise the function it claims to exercise;

  * a control whose fixture does not actually carry the mutation it
    claims to carry -- for example a section whose type was meant to be
    0x13 but whose offset makes the PRE-REPAIR validator refuse it for an
    UNRELATED reason, which would make the control pass on the
    PRE-REPAIR tree for the wrong reason;

  * a control whose positive control does not distinguish the repaired
    behaviour from the unrepaired behaviour;

  * a fixture that is read from a path the production code does not
    actually consult.

WHAT TO LOOK FOR.

The subject is an EVIDENCE HARNESS. Its whole purpose is to produce
observations that a reviewer can trust. A defect in it is a defect in the
EVIDENCE, even when the harness itself works.

Read the harness, the comparator, the contract, the emission verifier and
the probe, and ask, for each one:

  * Does the code do what its comment says?

  * Is there a path on which the code does something ELSE?

  * Is there a bound that is computed in a way that can overflow?

  * Is there a place where a value is read from uninitialised memory?

  * Is there a place where the argument list exceeds the production
    compiler's calling convention's limit?

  * Is there a place where a REASON TOKEN is reported that does not
    describe what actually happened?

  * Is there a place where the production function is DUPLICATED, so that
    the probe exercises the duplicate rather than the production code?

The compiler's calling convention has a KNOWN defect: a pointer-to-
pointer argument at parameter position eight or later is placed on the
stack by the call site and read from a register by the callee, so the
arguments that follow are shifted. Every function added or changed in
this round therefore takes at most seven parameters, or carries its
inputs in a context object that is filled BY NAME. Look for a function
that VIOLATES that rule.

The compiler's `&` operator does NOT behave as a bitwise AND on a hex
literal: `0x18EB1AFA & 0xF000` evaluates to `0x1000`. The shared
contract avoids the operator for this reason. Look for a new use of `&`
on a hex literal.
