R8_01_HERMETIC_INSTALL_PREFIX
    RED:    An isolated checkout at the entry head, with an EMPTY build
            directory, fails `make driver-wp001-correction03-test` with
            ELEVEN of the thirty-three positive controls failing.
            The compiler child's captured stderr is

              ERROR: Failed to open file: /usr/local/include/tos.HH

            The child's ACTUAL argument vector, read from the capture
            record's ARGV block, is

              <staged-producer>
              -c
              -o
              artifact.bin
              <staged-source>

            -- there is NO `--install-dir` option, so the compiler fell
            back to its compile-time default, `/usr/local`.
            The child's exit status was 1 and the artifact was absent.
            (red-p1-1-fresh-isolated-suite.log)
    REPAIR: The HARNESS -- the execution owner -- resolves the
            CONFIGURED test prefix and INJECTS `--install-dir <prefix>`
            into the child's argument vector when the caller supplied
            none. The prefix is read from the runner's own BINDING LIST
            (`HCC_TEST_PREFIX`), which is the repository's existing
            convention, and the PROBES forward the Makefile's exported
            `HCC_TEST_PREFIX` to the harness in that binding list.
            A CONFIGURED but UNPOPULATED prefix is a REFUSAL with the
            new reason token `HARNESS_PREFIX_UNPOPULATED`: the runner
            never degrades to `/usr/local`.
            The option is emitted in the compiler's OWN two-element form,
            because the production option table declares `--install-dir`
            with arity ONE and refuses the inline `--install-dir=<path>`
            spelling.
            The capture record carries a new `INSTALL_DIR` field, so the
            prefix the child received is directly readable.
    GREEN: The child receives `--install-dir <prefix>`, and the capture
            record's ARGV block names it. The child reads
            `<prefix>/include/tos.HH` and `<prefix>/lib/libtos.a`.

R8_03_OUTPUT_DASH_CLASSIFICATION
    RED:    The harness derived the output MODE from the output option's
            VALUE:

              if (StrCmp(out_value, "-") == 0) stdout_mode = 1;

            The two CLI forms are DIFFERENT, and the review confirmed it
            against the production compiler:

              -o-    284 bytes on stdout, NO file artifact
              -o -   0 bytes on stdout, a FILE named "-"

            The scan set `out_value = "-"` for BOTH, because the `-o-`
            spelling was modelled as an inline value. A genuine `-o -`
            request was therefore classified as a STDOUT emission, and
            the runner REWROTE the child's option.
    REPAIR: The output MODE is a property of the option's SPELLING, and
            the SCAN now reports it: only the compiler's own
            zero-argument stdout spellings (`-o-`, `--output=-`) select
            the stdout mode; every other spelling -- including `-o -`,
            whose VALUE is "-" -- selects the file mode.
            The probe's new `outmode` mode verifies BOTH forms against
            the DIRECT compiler invocation, and it accounts for the
            runner's output-path rewriting explicitly: the `-o -`
            control requires the record to name the FILE mode, the
            artifact to be present on the disk, and the artifact's
            ACTUAL digest to equal the digest the record claims.
