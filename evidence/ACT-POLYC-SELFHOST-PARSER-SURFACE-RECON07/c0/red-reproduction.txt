# FIRST HALF -- the PARTIAL forgery is REJECTED.

# to YES, leaving r0=2:

#
# The partial forgery is REJECTED: SUB-005 stays ineligible because the
# checker recomputes every clause from the FACT fields and the r0=2
# fact still fails clause 03.
#
# SECOND HALF -- the MAXIMAL forgery is ACCEPTED, and THAT IS THE
# FINDING.
#
# Forge EVERY fact of SUB-005: r0=0, all the flags YES, all the
# counters 0:
#
COMMAND=./build/parser-slice-recon03-eligibility <facts-with-SUB-005-fully-forged>

SUB-001	NO	0011111111111	2
SUB-003	NO	0011111111111	2
TOTAL=17
ELIGIBLE=12
STATUS=PASS
EXIT=0
#
# FINDING: the canonical checker CANNOT detect a forged fact row.  It
# is a pure function of its input facts; that is exactly why the
# input schema has NO `eligible` column (the eligibility FLAG cannot
# be forged) while the FACT fields still can.  The defence against a
# forged fact row is therefore NOT the checker but:
#
#   (a) the SOURCE-BOUND fact verification (MODE=DEPENDS), which
#       re-derives the SUB-005 dependence from the live bytes and
#       reports DEPENDENCE_SITE=TRANSITIVE_THROUGH_A_CALLEE; and
#   (b) the C3 INDEPENDENT re-derivation of every clause from the raw
#       facts, joined by exact candidate ID and source-range hash.
#
# Both are exercised in this ACT and both reject the forgery.
#
