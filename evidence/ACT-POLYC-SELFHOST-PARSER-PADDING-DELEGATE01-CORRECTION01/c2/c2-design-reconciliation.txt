## Measured consequence in the four production binaries

Each generation's build directory records the effective compile
definitions and the presence of the PolyC authority symbol:

| Generation | `HCC_USE_SELFHOST_PARSER_PADDING` in defines | `_BootstrapCalcPadding` in binary | Authority |
|---|---|---|---|
| G0 | 0 (absent) | 0 (absent) | Legacy C |
| G1 | 1 | 1 | PolyC |
| G2 | 1 | 1 | PolyC |
| G3 | 1 | 1 | PolyC |

The G0 row is the decisive one: the stage0 control does NOT activate the
PolyC-padding authority, so the six-way comparison is a real
legacy-vs-PolyC differential, not a PolyC-vs-PolyC tautology.

## Legacy stage0 path is EXPLICIT and still reachable

The legacy C algorithm body survives only inside the `#else` branch of
`src/parser.c::CalcPadding`, compiled without the macro in the stage0
evidence path. In the G0 production binary:

```text
$ nm build/padding-delegate-corr01/g0/hcc | grep -i CalcPadding
000000010003acd8 T _CalcPadding
000000010003acfc T _ParserLegacyCalcPaddingOracle
```

Both the legacy `CalcPadding` and the oracle wrapper are present in G0
and are the load-bearing implementation there.
