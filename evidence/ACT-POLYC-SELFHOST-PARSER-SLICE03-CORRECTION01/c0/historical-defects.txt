D1 ROOT CAUSE: THE 32-BIT OUTPUT FORMATTER
============================================

The predecessor tool computed the extremes CORRECTLY and destroyed
them on OUTPUT.  Its app_i helper formats with snprintf "%d":

  tools/quality/parser-slice03-contract-requalify.HC:79
    I64 m = snprintf(dst + n, cap - n, "%d\n", v);

"%d" is a 32-bit conversion.  The four computed extremes therefore
rendered as 0, 1, -1 and -2 -- exactly the observed F069..F072.

The VALUES THEMSELVES ARE CORRECT.  A C-side "%lld" printer shows
the full 64-bit value.  Measured with a PolyC probe linked against
a C printf helper (the probe is not a tracked artifact):

  I64 e0 = -9223372036854775807 - 1;   // INT64_MIN
  I64 e1 = -9223372036854775807;       // INT64_MIN+1
  I64 e2 =  9223372036854775807;       // INT64_MAX
  I64 e3 =  9223372036854775806;       // INT64_MAX-1

  e0=-9223372036854775808
  e1=-9223372036854775807
  e2=9223372036854775807
  e3=9223372036854775806

  snprintf(buf, 64, "%d\n",   e0) -> 0
  snprintf(buf, 64, "%lld\n", e0) -> -9223372036854775808

CONCLUSION: the defect is in the OUTPUT FORMAT of the producer, not
in the PolyC I64 arithmetic and not in the production precedence
semantics.  The correction uses a 64-bit format.

--- D6: THE LITERAL P16 ENUMERATION CANNOT FIT WITHIN THE 40-ROW PARTITION ---

The frozen P16 partition row declares:

  P16_BOUNDARY_INTEGERS	INT64_MIN, INT64_MIN+1, INT64_MAX-1, INT64_MAX, 0, -1, 1, and (each table value -1) and (each table value +1)	0	-1	40

  value_list     = INT64_MIN, INT64_MIN+1, INT64_MAX-1, INT64_MAX, 0, -1, 1,
                  and (each table value -1) and (each table value +1)
  value_count   = 0
  min_rows       = 40

The literal enumeration REQUIRES:
    4 extremes + 3 base values + 39 table values -1 + 39 table values +1
  = 4 + 3 + 39 + 39 = 86 entries before de-duplication.

The DISTINCT value set derived from the live 39-entry table is:
    58 distinct operator-neighbour values
    4 signed-I64 extremes
    3 additional base values (0, -1, 1)
    --
    65 distinct P16 values

65 > 40, so the literal enumeration CANNOT fit inside the frozen
40-row partition.  The predecessor resolved the contradiction by
TOPPING THE PARTITION UP TO 40 and truncating the neighbour sweep,
which silently dropped 25 of the 58 required neighbours AND all four
signed-I64 extremes (D1).

  neighbours actually emitted  = 25
