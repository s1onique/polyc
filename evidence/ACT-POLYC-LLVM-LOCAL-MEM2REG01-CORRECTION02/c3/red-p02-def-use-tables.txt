CASE_B_OPCODE_SET = {iadd, isub}

Derivation:
  $ awk '/    [a-z]+ +%l[0-9]+ i64 local/ {print $1}' \
        c3/fixture-*/pre-ir.txt | sort -u
  iadd
  isub
  ret        <-- terminator; not a definition opcode
  store      <-- case (a) already enumerated in §2 rule 3

  'iadd' and 'isub' are the ONLY scalar-arithmetic opcodes
  whose dst is an i64 local in the current neutral IR of
  the six fixtures. No other integer-arithmetic opcode
  (imul, and, or, xor, shl, shr, udiv, sdiv, urem, srem,
  umulh, smulh, neg, not) appears as a local-dst in any
  fixture today. This set is the ELIGIBLE-FIXTURE minimum;
  no speculative widening. A wider set requires a future
  ACT after evidence exists (per §2 rule 3).

The frozen CASE_B_OPCODE_SET is therefore exactly the
opcodes required by the eligible fixture definitions
discovered in this RED.

  bb.id    exact neutral-IR instr                                opcode   case
  bb1      "store    %l2 i64 local, %p1 i64 param  ; line 1"     store    (a) IR_STORE-source
  bb5      "iadd     %l2 i64 local, %l2 i64 local, %l6 i64"      iadd     (b) scalar-arithmetic-dst
            (self-referential: RHS uses %l2, dst is %l2; case (b)
             covers this because the dst is a local and the opcode
             is in the frozen case-(b) set)

read sites:
  bb.id    exact neutral-IR instr                                opcode
  bb5      "iadd     %l2 i64 local, %l2 i64 local, %l6 i64"      iadd  (RHS read of %l2; case-(b) RHS source)
  bb4      "store    %t5 i64 tmp, %l2 i64 local  ; line 8"       store (compiler-generated return handling)

address taken?                      no
GEP?                                 no
escape?                              no

definite assignment:
  for EVERY read, does every executable entry->read path
  contain a reaching definition?       yes
  evidence/path justification:
    bb5's `iadd %l2 = %l2 + %l6` requires %l2 to be defined
    BEFORE the iadd on every path to bb5.
    bb5's only predecessor is bb3, and bb3's only
    predecessor is bb1. bb1 store-defines %l2 = %p1.
    So every entry->bb5 path passes through bb1 and finds
    the bb1 store of %l2.
    bb4's store-to-return-slot: paths are bb1, bb1->bb3,
    and bb1->bb3->bb5. All carry the bb1 store of %l2,
    possibly refined by bb5's iadd.

feeds compiler-generated return handling?  yes
  bb4's `store %t5 i64 tmp, %l2 i64 local` is the
  compiler-generated return-slot store.
