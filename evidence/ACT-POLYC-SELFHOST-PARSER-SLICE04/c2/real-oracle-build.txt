THE ORACLE OBJECT IS BYTE-IDENTICAL TO THE ENTRY PRODUCTION OBJECT
-------------------------------------------------------------------

The C0 entry recorded the freshly built production ast.c object as
sha 144c9836ba79125bd973f9faefe05b259e9efaa1e8bc7babc5c44de007de7253
(c0/baseline-conservation.txt).  The oracle object built now has the
SAME sha.  The oracle therefore executes the EXACT legacy code the
production build executed before the migration -- not a copy of it,
not a paraphrase of it, not a reimplementation.

  ORACLE_IS_BYTE_IDENTICAL_TO_THE_ENTRY_PRODUCTION_OBJECT=YES

THE ORACLE DOES NOT DEPEND ON THE POLYC SYMBOL
------------------------------------------------

COMMAND=nm build/slice04-ast-legacy.o | grep -c BootstrapAstBinOpFromToken
OUTPUT=0

  ORACLE_REFERENCES_POLYC_SYMBOL=NO

The build rule ENFORCES this: it fails the build if the object
references _BootstrapAstBinOpFromToken, because that would mean the
delegation flag was NOT off and the "oracle" would be the PolyC
component compared against itself.

THE DRIVER CONTAINS NO MAPPING TABLE
-------------------------------------

  DRIVER=tools/quality/parser-slice04-oracle-driver.c
  DRIVER_ADAPTER=tools/quality/parser-slice04-oracle-adapter.c

The driver calls the real function with a PREINITIALISED output slot
(the distinguished value 12345, outside the live AstBinOp range 0..28)
and reports the observed success flag and the final enum value.  The
adapter (Slice04LegacyBinOpOracle) is the same shape, for the
differential.

Neither file contains a mapping table: the mapping is the live
src/ast.c's.

  DRIVER_CONTAINS_A_MAPPING_TABLE=NO
  ADAPTER_CONTAINS_A_MAPPING_TABLE=NO

THE STUB
--------

  STUB=tools/quality/parser-slice04-oracle-stub.c

The stub defines `int is_terminal = 0;` so the oracle can link against
the production objects without main.c.  It follows the SLICE03
precedent and contains no mapping logic.

  STUB_CONTAINS_MAPPING_LOGIC=NO
