THE SELECTION IS NOT MADE AT C0
================================

C0 establishes the RED and the baseline.  It does NOT name a winner.
The mechanical selection happens at C1 using the binding eligibility
checker and the RECON03 lexicographic ranker:

  tools/quality/parser-slice-recon03-eligibility.HC   (13 clauses)
  tools/quality/parser-slice-recon03-ranking.HC       (R0..R6)

Both are existing, closed, PolyC tools.  SLICE04 reuses them against
SLICE04's own candidate inventory; it does not author a new ranker and
does not change the R0..R6 dimension definitions.

The ranker consumes an ELIGIBILITY-VERIFIED input: its `eligible`
column is the OUTPUT of the eligibility checker, so an ineligible
candidate with artificially perfect ranking scores can never win.

THE TWO CANDIDATES' SEMANTIC SHAPES AT ENTRY
=============================================

Both candidates have the identical API shape:

  int astBinOpFromToken(s64 op, AstBinOp *_result);
  int astUnaryOpFromToken(s64 op, AstUnOp *_result);

Both:
  1. return 1 when the token maps to an AST operator;
  2. return 0 otherwise;
  3. write the enum value through `result` only on success;
  4. leave the caller's existing result value unchanged on failure.

All four properties are binding for the replacement.

THE SCOPE OF THE MIGRATION IS EXACTLY ONE FUNCTION
===================================================

The selected candidate's C decision leaves the production path.  The
NON-SELECTED candidate stays legacy C and must remain byte-identical
unless build-conditional wrapping absolutely requires a shared
formatting change, which would need prospective C1 authorization and
an exact semantic conservation witness.

At entry both functions live in the same file and the same #ifdef
style used by the three qualified predecessors.  Whether a shared
formatting change is needed is determined at C1 and recorded in
c1/implementation-scope.txt before any production edit.
