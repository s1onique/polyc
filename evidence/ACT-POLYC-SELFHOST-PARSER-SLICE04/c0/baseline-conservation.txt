THE FRESH-TREE PROOF (F9)
=========================

F9 requires fresh-tree evidence for closure-critical compiler gates.
The C0 RED was therefore measured against a FRESH build tree, not
against the repository's ignored build/ directory:

COMMAND=rm -rf /tmp/slice04-red-build
COMMAND=cmake -S ./src -B /tmp/slice04-red-build -G 'Unix Makefiles' \
          -DCMAKE_C_COMPILER=cc -DCMAKE_BUILD_TYPE=Release \
          -DHCC_ENABLE_JIT=on -DHCC_ENABLE_LLVM=OFF
COMMAND=make -C /tmp/slice04-red-build -j4
OUTPUT=BUILD=OK

The freshly built production object:

  /tmp/slice04-red-build/CMakeFiles/hcc.dir/ast.c.o
  SHA256=144c9836ba79125bd973f9faefe05b259e9efaa1e8bc7babc5c44de007de7253

This object was produced by the command above, so its contents cannot
be a stale artifact carried over from a previous build.

THE STALE-ARTIFACT HAZARD IS EXPLICITLY EXCLUDED
==================================================

build/ is listed in .gitignore, so objects under it are untracked and
can survive from an unrelated build.  Two independent mechanisms
exclude them from the RED and from every later conservation claim:

  (1) The RED was measured on /tmp/slice04-red-build, a directory
      created by the command above in this session and containing
      only objects built from the entry tree.

  (2) The C2 build integration (ACT section 8.3) makes the object
      VERIFICATION a custom TARGET rather than an OUTPUT-producing
      custom command, so the verification command ALWAYS runs and a
      stale stamp file can never decide that the verification is
      unnecessary.  This is the SLICE03 discipline, inherited here.

The RED additionally cannot be produced by a missing component that
some other object happens to satisfy: the C0 RED asserts the ABSENCE
of a PolyC symbol across the whole fresh build, and the C2 fail-closed
build gate requires a STRONG GLOBAL definition of exactly the one
expected symbol in exactly the selected object.

THE DISASSEMBLY PROVES THE DECISION IS STILL IN C
-------------------------------------------------

The presence of the symbol alone would not prove that C still owns the
DECISION.  The disassembly of the freshly built production object
does prove it:

COMMAND=otool -tvV /tmp/slice04-red-build/CMakeFiles/hcc.dir/ast.c.o \
          | awk '/_astBinOpFromToken:/,/^$/'

The body is a two-level jump table over the token value:
  sub  x9, x8, #0x25       ; token - 0x25 ('%')
  cmp  x9, #0x57           ; the ASCII window
  b.hi ...
  ldrb w12, [x10, x9]      ; jump-table byte
  br   x11                 ; dispatch
  ...
  sub  x8, x8, #0x309      ; TK_SHL .. TK_SHR window
  ...
  mov  w8, #0x2            ; AST_BIN_OP_ADD
  mov  w8, #0x5            ; AST_BIN_OP_SUB
  mov  w8, #0x0            ; AST_BIN_OP_MUL
  ...
  mov  w8, #0x10           ; AST_BIN_OP_SHL
  mov  w8, #0x11           ; AST_BIN_OP_SHR
  str  w8, [x1]            ; write the enum through the output pointer
  mov  w0, #0x1            ; return 1
  ret

Every enum value is MATERIALISED AS AN IMMEDIATE IN THE PRODUCTION
OBJECT.  The token-to-operator classification is therefore executed
by C in the production build.  This is the real defect the ACT
retires, observed on the real production seam.

  SELECTED_COMPONENT_EXISTS=NO
  SELECTED_PRODUCTION_DELEGATION=NO
  SELECTED_POLYC_AUTHORITY=NO
  LEGACY_AST_MAPPING_AUTHORITY=YES

(These four predicates are recorded for BOTH candidates; the RED does
not presuppose which candidate will be selected.  See
candidate-scope.txt.)
