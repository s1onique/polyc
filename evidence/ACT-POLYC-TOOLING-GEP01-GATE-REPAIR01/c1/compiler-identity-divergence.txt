=== ACT-POLYC-TOOLING-GEP01-GATE-REPAIR01 :: C1 RED
=== Defect B: the harness's compiler and the verifier's compiler DIVERGE
===

The PolyC harness is parameterised by --hcc=<path>:

    tools/quality/llvm-gep01-test.HC
      hcc_path = ArgValue(argc, argv, "--hcc", "./hcc");
      ...
      RunPositives(v, hcc_path, install_dir, scratch_child, seed);

Every compiler-facing row uses that hcc_path. But the cap-table
verifier is spawned WITHOUT it:

    tools/quality/llvm-gep01-test.HC, RunCapability()
      args[0] = python;
      args[1] = StrPrint(NULL, "scripts/quality/llvm-cap-table-verifier.py");
      args[2] = NULL;

and the verifier hardcodes its own compiler:

    scripts/quality/llvm-cap-table-verifier.py:55
      HCC = REPO_ROOT / "hcc"

MEASURED DIVERGENCE
-------------------
$ ./hcc --print-cap-table ; echo $?
139                       <- SIGSEGV; stdout 0 bytes

$ strings hcc | grep -c CAPABILITY_COUNTERS
0                         <- non-LLVM build: no LLVM backend linked

$ strings build/hcc | grep -c CAPABILITY_COUNTERS
1                         <- LLVM build: backend present

WHY IT SEGFAULTS
----------------
The --print-cap-table dispatch lives inside #ifdef HCC_ENABLE_LLVM:

    src/main.c:437
      #ifdef HCC_ENABLE_LLVM
          if (args.print_cap_table) {
              #include "llvm-backend-cap.h"
              llPrintCapabilityTable();
              return 0;
          }
      #endif

On a NON-LLVM build the flag is still parsed (src/cli.c:523 sets
args->print_cap_table = 1) but nothing handles it. The compiler then
falls through to the normal compile path with NO input file and dies on
SIGSEGV (exit 139).

CONTRAST: THE SAME VERIFIER, TWO COMPILERS
-------------------------------------------
$ python3 scripts/quality/llvm-cap-table-verifier.py     # non-LLVM ./hcc
FAIL  hcc --print-cap-table exited non-zero:
FAIL  could not load capability table from hcc --print-cap-table
(rc=1)

$ python3 scripts/quality/llvm-cap-table-verifier.py     # LLVM ./hcc
PASS  loaded 56 capability rows via hcc --print-cap-table
...
PASS: dispatch <-> capability <-> harness bound
(rc=0)

The verifier's verdict therefore depends on a binary the HARNESS NEVER
TOLD IT ABOUT. That is the contract violation this ACT repairs.

CONSEQUENCE FOR THE FOUR ROWS
------------------------------
When the verifier fails, the harness reports three identical rows
("could not read cap verifier output"), so the operator sees 4 failing
rows and cannot tell that they are TWO distinct defects. This ACT's
probes isolate them.
