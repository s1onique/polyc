CONCLUSION (mechanical, with witness numbers)
    AC-05 (which source shapes trigger which path):
        Source shape                                   IR_BR path
        -------------------------------------------    -----------
        local/param ref + non-ICMP (witnesses 1,8)     normalized
            (because locals are loaded with movzbq/movslq
             first, then the load result is i64 in the
             IR_BR operand; src/ir.c:107 takes the
             non-i8 path and inserts cmp_ne)
        explicit comparison (witnesses 3,7)            normalized
        arithmetic result (witnesses 9,10)             normalized
            (arithmetic widens operands to i64)
        I16/I32/I64 non-ICMP source (witness 6)        normalized
            (these are non-I8 types; cmp_ne inserted)
        U8/I8 function-call return (witnesses 2,4,5)   BYPASS
            (the call result is IR_TYPE_I8; irBranch sees
             cond->type == IR_TYPE_I8 and skips cmp_ne)

    The bypass is triggered specifically when:
        cond->type == IR_TYPE_I8
            AND
        cond is NOT the immediate dst of an IR_ICMP/IR_FCMP
            AND
        the source shape yields i8 (function-call return,
            struct field access, array load, etc.)

    All other shapes are normalized.

CORRECTION TO CORRECTION01

    The CORRECTION01 ACT claimed:
        "The VALUE of an IR_ICMP result is set by the native
         SETcc instruction ... which by x86 architecture yields
         exactly {0, 1} in the destination byte/register.
         Therefore in cases (a), (b), (c), the cond value is
         ALWAYS in {0, 1}."

    This was incorrect. Cases (b) and (c) ARE in {0,1} (because
    they come from IR_ICMP, which IS produced via SETcc). But
    case (a) -- cond is already I8 and NOT from an immediate
    IR_ICMP -- bypasses normalization entirely. The conditional
    "in case (a), the I8 is the result of IR_ICMP(NE, v, 0)"
    was an inference that does not follow from src/ir.c:107-123.

    Per AGENTS.md F4, this claim is now downgraded. The IR permits
    arbitrary I8 values in IR_BR when the bypass class triggers;
    the backends compensate by treating the operand as the full
    register compared to zero.

CONSEQUENCE FOR LLVM (per ACT §32)

    The existing LLVM backend's narrow contract (I64 only) means
    the bypass class CANNOT reach LLVM IR_BR lowering. So the
    IR_BR correctness problem for LLVM is bounded by the
    normalized class (case b/c only), where IR_BR operands are
    in {0,1} and the existing trunc path at
    src/llvm-backend.c:594 is correct.

    The bypass class would surface ONLY if the LLVM backend's
    llTypeSupported is broadened to include IR_TYPE_I8 (a future
    ACT's decision). In that hypothetical case, a generic
    lowering for i8 IR_BR would need to mirror the native
    backends' testq/cmp semantics, not the SETcc/trunc semantics.

NEXT-ACT RECOMMENDATION

    ACT-POLYC-IR-BRANCH-CONDITION01 mission is now NARROWER, not
    wider. The two candidates are:

        (i)  Widen IR_BR_TYPE_CONTRACT to UNIFORM_I8_OR_I64:
             enforce a uniform representation at the IR_BR
             operand (e.g., always i8 OR always i64). This is
             what ACT-POLYC-IR-BRANCH-CONDITION01's predecessor
             suggested.

        (ii) Tighten IR_BR_VALUE_CONTRACT to a formal invariant
             that ALL producers of i8 IR_BR operands must come
             through a truthiness coercion (e.g., always emit
             `cmp_ne %bool, %x, 0` before the br, even when
             %x is already i8).

    The witnesses show the bypass class is RUNTIME-CORRECT for
    the existing native backends (full-register test). So the
    defect is REPRESENTER-FACING (LLVM future-proofing +
    backend portability), not user-visible today. The next
    ACT should select (i) OR (ii) and propose the bound.
