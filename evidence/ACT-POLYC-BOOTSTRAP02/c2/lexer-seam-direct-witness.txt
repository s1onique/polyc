============================================================
What the divergence MEANS
============================================================

(a) l->start_after diverges for all 6 cases:

    Legacy:  l->start_after  = offset of the first byte
             AFTER the identifier (= l->ptr_after for
             non-EOF cases). This is set by the LAST
             call to lexNextChar in the legacy
             identifier loop (line 949).

    Stage1:  l->start_after  = l->start_at_pre_call
             (= offset of the first identifier byte,
             set by lexCore's lexNextChar at the top
             of the dispatcher loop, line 1208).

    The B1 path (src/lexer.c:911-939) NEVER sets
    l->start; it only sets l->cur_strlen and l->ptr.
    So l->start retains whatever value lexCore's
    lexNextChar set it to.

    Is this observable downstream? Verified by grepping
    the production sources: l->start is read only
    inside lexCore at line 1209 (start = l->start),
    which is BEFORE lexIdentifier is called. After
    lexIdentifier returns, no consumer reads l->start
    until the NEXT lexNextChar overwrites it.

    Verdict: benign RESIDUE. Recorded for a future
    correction ACT.

(b) ptr_after diverges at E4 (EOF):

    Legacy:  l->ptr_after = offset of NUL at end of
             identifier (= 3 for "abc").
    Stage1:  l->ptr_after = offset of NUL + 1 (= 4
             for "abc").

    The B1 path (src/lexer.c:932-934) deliberately
    advances l->ptr one past the NUL when the
    identifier ends at NUL. The legacy path does
    not advance.

    The next lexNextChar after stage1's
    lexIdentifier would read src[4] (whatever is
    there; could be garbage in tests, or a real
    next character in real sources). For the
    HARNESS's "abc" (length 3, NUL-terminated in
    a zero-padded buffer), src[4] = NUL → next
    lexNextChar returns 0 → EOF correctly.

    In real production, lexCore's `case '\0':
    return 0;` (line 1243) handles EOF without
    recursion, so this divergence is benign in
    current callers.

    Verdict: latent RESIDUE. The B1 EOF cursor
    model differs from the legacy model; the next
    byte after EOF (read by the next lexNextChar
    after a stage1 lexIdentifier-at-EOF) may
    return garbage. Real callers (lexInclude,
    cctrl) handle EOF without further recursion,
    so the latent bug does not currently bite.

    Recorded for a future correction ACT.
