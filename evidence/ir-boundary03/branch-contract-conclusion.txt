LOWERING SHAPE (see branch-condition-producers.txt)
    case 1: IR_ICMP result (I64) -> IR_BR operand (I64).
            cond is the dst of the immediately preceding
            IR_ICMP; irBranch preserves it as-is.
    case 2: IR_ICMP(NE, v, 0) (I8) -> IR_BR operand (I8).
            cond is non-I8 and NOT an immediate IR_ICMP
            dst; irBranch inserts a coercion IR_ICMP(NE,
            v, 0) producing I8.

THREE-AXIS CLASSIFICATION
    The predecessor classification mixed three orthogonal
    axes. The reviewer correctly identified the conflation.
    The refined decomposition is:

    SOURCE_CONDITION_CONTRACT = I64_ZERO_NONZERO_TRUTHINESS
        scope: language level (HolyC/PolyC if (x) semantics)
        empirical: confirmed by six-determinator matrix;
            AOT and JIT agree
        proof: runtime test in src/tests/ir-boundary03/

    IR_BR_VALUE_CONTRACT = BOOLEAN_0_OR_1
        scope: neutral IR level
        empirical: NOT directly tested (no RED is needed;
            provable from source inspection alone)
        proof:
            1. irBranch (src/ir.c:97-136) is the sole
               producer of IR_BR (verified by
               branch-condition-producers.txt).
            2. irBranch accepts cond in three shapes:
                 (a) cond is I8:                case 2
                 (b) cond is dst of immediate
                     IR_ICMP:                   case 1
                 (c) anything else:             case 2
                     (inserted IR_ICMP(NE,v,0))
            3. irICmp (src/ir.c:80-94) is the sole
               producer of IR_ICMP results.
            4. The VALUE of an IR_ICMP result is set by
               the native SETcc instruction:
                 src/x86_64.c:1690 x86_64EmitSetCC
                 src/x86_64-jit.c:1166 jitEmitSetCC
               which by x86 architecture yields exactly
               {0, 1} in the destination byte/register.
            5. Therefore in cases (a), (b), (c), the cond
               value is ALWAYS in {0, 1}.
            6. The I64 vs I8 distinction is the OPERAND
               WIDTH (representation), NOT the value-domain.

        This is a strictly stronger claim than the
        predecessor MIXED_OR_UNPROVEN. The reviewer
        demonstrated the proof from src/ir.c alone.

    IR_BR_TYPE_CONTRACT = MIXED_I64_I8
        scope: representation width
        empirical: CONFIRMED as a latent bug
            (LLVM backend currently rejects I8 case 2 at
            src/llvm-backend.c:585; native AOT/JIT accept
            both widths)
        proof: branch-condition-producers.txt + dump-ir
            transcripts (case 1 produces I64 IR_BR operand;
            case 2 produces I8 IR_BR operand)
        target: ACT-POLYC-IR-BRANCH-CONDITION01

CONSEQUENCE FOR LLVM (per ACT §32)
    The LLVM backend currently lowers I64 case 1 via
    LLVMBuildTrunc (i64 -> i1, parity trunc). For values
    in {0, 1} this is correct (0 -> 0, 1 -> 1) by the
    IR_BR_VALUE_CONTRACT. It would be WRONG for arbitrary
    I64 values, but the IR shape guarantees the value is
    in {0, 1} because the only producer is IR_ICMP (per
    case (b)) or the explicit IR_ICMP(NE, v, 0) coercion
    (per case (c)). So the existing LLVM lowering is
    correct BY THE VALUE-DOMAIN CONTRACT, which is now
    PROVEN (was MIXED_OR_UNPROVEN in the predecessor ACT).

    For I8 case 2, the existing LLVM backend CANNOT
    currently lower the IR_BR (it requires I64 at line 585).
    This is a latent defect — the I8 rejection is the
    IR_BR_TYPE_CONTRACT issue, not a value-domain issue.

NEXT-ACT RECOMMENDATION
    The branch-contract classification is now three-axis:
        SOURCE_CONDITION_CONTRACT = I64_ZERO_NONZERO_TRUTHINESS
        IR_BR_VALUE_CONTRACT      = BOOLEAN_0_OR_1
        IR_BR_TYPE_CONTRACT       = MIXED_I64_I8

    The next ACT is ACT-POLYC-IR-BRANCH-CONDITION01 with
    mission: prove and mechanically enforce the IR_BR_TYPE_CONTRACT
    uniform I8-or-I64 representation, and add the explicit
    zext I8 -> I64 in the lowering for case 2 (or, equivalently,
    uniform the case-1 IR_ICMP result to I8). This is a
    SOURCE-LEVEL clarification, not a type system change
    (no IR_TYPE_I1 introduced).

    The IR_BR_VALUE_CONTRACT is settled by THIS ACT's source
    inspection and does not require a separate bounded ACT.
